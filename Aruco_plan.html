Attitude Node: attitude_node.py

Inputs: /aruco/markers (PoseArray), /aruco/marker_ids (Int32MultiArray), /odometry/filtered (EKF yaw for latch reference)

Output: /aruco/attitude (PoseWithCovarianceStamped, yaw-valid only)

Frame: All base-frame operations in base_footprint — already used by AMCL, costmaps, diff_drive. TF lookup zed_camera_link → base_footprint from URDF chain.

Data Flow

1 Subscribe to all three inputs
2 Look up zed_camera_link → base_footprint TF (cached, fallback identity)
3 For each marker: rvec → rotation matrix → wall normal → transform to base_footprint → psi = atan2(normal.y, normal.x)
4 Latch: if not latched (first detect OR loss > 0.5s): psi_ref = circular_mean(all psi), yaw_ref = latest EKF yaw from /odometry/filtered
5 Differential: psi_mean = circular_mean(all psi, this frame); yaw_obs = yaw_ref + circular_delta(psi_mean - psi_ref)
6 Inter-marker agreement: reject frame if max pairwise |psi_i - psi_j| > yaw_threshold
7 Jump rejection: reject if |yaw_obs - last_published| > jump_threshold
8 Dynamic covariance: rolling window of last N accepted yaw_obs → empirical stddev → clamp(min_cov, max_cov) → covariance[35]
9 Publish /aruco/attitude
10 Loss recovery: if no valid markers for > 0.5s → reset latched flag → re-latch on next detection

Section 3 — Navigate to ArUco Marker FUTURE

Concept

Marker-Relative Goals

The robot navigates toward a detected ArUco marker rather than absolute (x, y) coordinates. The marker pose is transformed to map frame via TF, an approach offset is computed, and the goal is sent to Nav2's navigate-to-pose pipeline.

Use case: Docking stations, inspection points, marker-defined corridors.

Search & Re-acquire

If the target marker is not visible, the robot executes a search pattern (rotate, move forward, repeat) until the marker is detected.

Use case: Lost marker recovery, entering a marker-marked zone from arbitrary approach angle.

Precision Docking

Nav2 navigates to a staging pose near the dock. Then vision-based final approach using the ArUco marker for cm-level precision.

Use case: Autonomous charging, tool docking, payload pickup.

SearchMarker C++

Registers as a Nav2 behavior plugin (alongside Spin, Backup, DriveOnHeading, Wait). Rotates in place, then expands outward until the target marker is detected.

class SearchMarker : public Behavior {
  // 1. Rotate in place (configurable speed)
  // 2. If not found after full rotation, move forward
  // 3. Repeat expanding search pattern
  // 4. SUCCESS when marker detected
  // 5. FAILURE on timeout

Section 4 — ERC Traverse: Scored Waypoint Navigation FUTURE

Task Overview

The ERC Autonomous Traverse task requires:

  1. Start at the Starting Point
  2. Reach four waypoints (A, B, C, D) in any order
  3. Return to the Starting Point
  4. Execute the submitted Traversal Plan

ArUco poles serve as navigation aids distributed around the Marsyard — they are not waypoint targets. At least two markers must be visible from the starting position.

Scoring Model

Waypoint Distance Score

For each of four waypoints, score is:

Pwp = max(0, round(30 − 6d))

where d is the distance in metres from the nearest edge of the rover body to the waypoint.

Body-edge to waypoint dPoints per waypoint
0 m30
0.5 m27
1.0 m24
2.0 m18
3.0 m12
4.0 m6
≥ 5 m0

Critical distinction: Waypoint scoring uses the nearest point on the rover's physical outline. Return-to-start uses the rover's geometric centre within 1 m. The planner must use two separate termination criteria.

Score Budget

ElementMaxCondition
Four waypoint distance scores120Up to 30 each via distance formula
Waypoint autonomy10025 per waypoint reached autonomously
Return to start25Geometric centre within 1 m, after ≥ 1 waypoint
Autonomous return25Return executed autonomously
Traversal Plan execution30Pre-planned route was actually followed
Traverse total300Before penalties

Tuning Guidance

  • < 1 m body-edge distance → 24–30 points per waypoint
  • < 0.5 m for near-maximum score
  • Account for rover footprint: distance from base_link centre ≠ body-edge distance
  • Set Nav2 goal tolerance conservatively (e.g., 0.3 m centre-based) and stop before the judge measures

Nav2 BT Plugins

NavigateToWaypoint C++

BT action node. Sets Nav2 goal for a waypoint ID with known (x, y). Monitors body-edge distance during approach and terminates when within target threshold.

class NavigateToWaypoint : public BtActionNode {
  // 1. Look up waypoint (x, y) by ID
  // 2. Convert body-edge target to centre-based radius
  //    using minimum body radius in approach direction
  // 3. Send goal to NavigateToPose
  // 4. Monitor body-edge distance during approach
  // 5. SUCCESS when threshold reached
  // 6. Log achieved distance for scoring
};

<NavigateToWaypoint waypoint_id="A" target_body_edge_m="0.3"/>

ReturnToStart C++

BT action node. Special terminal behavior. Uses geometric centre check (not body-edge). Terminates when centre-to-start ≤ 1.0 m.

class ReturnToStart : public BtActionNode {

  // 3. SUCCESS when centre-to-start ≤ 1.0 m
  // 4. FAILURE on timeout
};

<ReturnToStart start_x="0.0" start_y="0.0"/>

Waypoint Mission Format

Waypoints are defined by ID with known map-frame coordinates. The Traversal Plan specifies the intended visit order (scored at 30 pts).

traverse_waypoints:
  starting_point: [0.0, 0.0]
  waypoints:
    A: {x: 10.0, y: 5.0, target_body_edge_m: 0.3}
    B: {x: 20.0, y: 0.0, target_body_edge_m: 0.3}
    C: {x: 15.0, y: -8.0, target_body_edge_m: 0.5}
    D: {x: 5.0, y: -4.0, target_body_edge_m: 0.3}
  return_threshold_centre_m: 1.0

Traversal Plan logging — the BT must record for post-mission verification:

  • Visited waypoints and their order
  • Achieved body-edge distances per waypoint
  • Timestamps for mission reconstruction
  • Whether each waypoint was reached autonomously

ArUco Marker Distribution

ERC material states ArUco markers are distributed around the Marsyard as navigation aids, not waypoint targets:

  • At least two markers visible from the starting position
  • Distributed around the Marsyard to provide visual references during traversal
  • Serve as inputs to Phase 2b (visual yaw correction via attitude_node)
  • Used by SearchPattern as re-localization landmarks
  • Not required at waypoint locations
